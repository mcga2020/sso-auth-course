第 5 课 · 迁移实战

CAS → OIDC 迁移专题

双轨并存、灰度切换、坑点清单——把前面四课的知识组装成一份行动方案。

约 12 分钟 前置：第 4 课 速查：术语表

到此刻，你手里已经有全部零件：CAS 时序（第 2 课）、会话分层（第 3 课）、OIDC 流程（第 4 课）。这一课只做一件事——组装：你们公司的登录体系怎么从「应用 → CAS 层 → PingFederate」搬到一个新形态。

先说结论（本课 = 阶段一） 本课方案：应用从对接 CAS 层改为直连 PF 的 OIDC 端点，CAS 层逐步退役。它同时也是整个迁移的阶段一——公司终局是自研 IdP 接棒 PF（阶段二）。两段式的精髓：阶段一让应用从此只认 OIDC 标准，阶段二换 IdP 时，应用侧就从「改代码」降级成「改配置」。密码核对位置不变（先 PF、后新 IdP 委托现有账号源），用户全程无感。

§1目标架构：搬家前 vs 搬家后

现状（三层）
  应用 ──CAS 协议──▶ Apereo CAS ──委托(SAML/OIDC)──▶ PingFederate

阶段一目标（本课）：拆掉 CAS 层
  应用 ──OIDC 直连──▶ PingFederate        ← /as/authorization.oauth2
                                          ← /as/token.oauth2

阶段二目标（终局）：自研 IdP 接棒 PF
  应用 ──OIDC 直连──▶ 自研 IdP ──核对密码──▶ 现有账号源（AD/LDAP/用户库）

中间态（双轨并存，本课主角）
  应用A ──CAS──▶ CAS 层 ──委托──▶ PF      ← 还没搬的
  应用B ──OIDC──────────────────▶ PF      ← 已搬的

注意中间态里：CAS 层和 PF 都活着，新旧应用各走各的门。迁移的全部难度都浓缩在这个「双轨并存期」——通常持续数周到数月。

§2双轨期的核心难题：会话孤岛

第 3 课埋的伏笔这里回收。切换日，海量用户身上挂着三层旧会话：

旧会话认哪门语言应用改说 OIDC 后它的命运
应用本地会话应用自己的 Cookie照常有效——本地会话不依赖任何 IdP，切协议碰不着它
CAS 层 TGT/TGCCAS 协议对已迁移应用失效成孤岛——它只在用户再访未迁移应用时才被用到
PF 层会话PF 自己的 Cookie继续有效——迁移后登录直连 PF，有它照样免密直通（第 4 课图 1 第 3 步）

于是「孤岛无害化三原则」：① 不强行迁移会话（没有干净的跨协议搬会话手段，别发明）；② 让孤岛自然消亡——TGT 按既有超时策略过期即可，什么都不用做；③ 登出语义兜底——双轨期用户在旧应用登出、新应用可能还活着（反之亦然），要么接受这个窗口期，要么在 PF 侧配统一登出策略。

一个意外的好消息 因为 PF 层会话双轨通用，用户上午在旧体系登录过、下午访问已迁移的新应用——第 4 课图 1 第 3 步 PF 认出自己的会话 Cookie，免密直通。所以切换日用户体验是「无感」的，多数用户根本不知道发生了迁移。

§3灰度七步清单

图 1 · 单个应用的迁移步骤（跑通后复制到下一个）
1
在 PF 注册 OIDC 客户端 client_id、redirect_uri 白名单、scope（openid）、claims 映射（sub → 工号）——找 PF 管理员完成
2
挑试点应用：小流量、易回滚、代码新 内部工具 > 边缘业务 > 核心系统，顺序别反
3
应用实现授权码流程（带 state + nonce + PKCE） 主流框架都有现成客户端库，别手写协议细节
4
测试环境全流程验收 拿第 4 课图 1 的 8 步逐帧对照，重点盯：state/nonce 校验、ID Token 五项验证、错误分支
5
灰度上线并观测 登录成功率、回调报错率、平均耗时；保留旧 CAS 代码路径作为回滚开关
6
复制推广到其余应用 把第 3 步沉淀成团队模板/脚手架，越搬越快
7
CAS 层退役 先关新登录入口，等 TGT 全部自然过期（观察一个最长寿命周期），再下线服务器

§4坑点清单（含一个隐形炸弹）

坑症状解法
redirect_uri 不一致PF 拒绝跳转 / 回调 404老朋友：逐字符比对，含协议、端口、路径、末尾斜杠；先在测试环境过一遍
用户标识映射断裂 💣迁移后登录成功但「变成了新用户」，历史数据对不上核对 CAS 时代 /serviceValidate 返回的 user 与 OIDC 的 sub 是否同一标识体系（工号 vs 邮箱 vs UUID）。不一致就先在 PF 侧调 claims 映射。这是最容易被忽略、后果最重的一个
漏验 state / nonce安全扫描亮红灯 / 理论可重放用成熟库默认行为，别自作主张省略校验
时钟偏差ID Token 间歇性判为过期exp/iat 验证前确认应用服务器 NTP 同步；可容忍小偏移，但别关掉校验
公钥轮转某天凌晨起全部验签失败别把 JWKS 公钥写死在配置里——按发现端点动态拉取并定期刷新
登出语义变化「登出了还登着」投诉增加CAS 的 SLO 是自动逐站通知；OIDC 默认没有等价物，需在 PF 配置登出端点（RP-initiated / front/back-channel 概念，落地时查 PF 文档），双轨期尤其要测
代理票据（PT）应用服务间转授场景断掉CAS 的 PGT/PT 在 OIDC 没有直接对应物；若真有应用在用，需单独设计（如 client credentials 流），提前排查
阶段二预告：issuer 更替未来换自研 IdP 时全部验签失败应用侧从一开始就按发现端点动态获取配置（而非写死每个 URL）；sub 用户标识在两个 IdP 间保持同一取值体系——阶段一的映射纪律，决定阶段二是改配置还是改代码

本课要点

  1. 终局：PF 不动，应用直连其 OIDC 端点，CAS 层退役；密码核对自始至终在 PF。
  2. 双轨期：应用本地会话照常、TGC 成无害孤岛自然消亡、PF 会话双轨通用（用户基本无感）。
  3. 灰度七步：PF 注册客户端 → 试点应用 → 授权码流程 → 逐帧验收 → 灰度观测 → 复制推广 → CAS 自然退场。
  4. 头号坑：用户标识映射（user vs sub）——上线前必须核对，其余坑见 §4 清单。
