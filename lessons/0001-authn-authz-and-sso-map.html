第 1 课 · 认证地基

认证 vs 授权：一次登录背后发生了什么

在接触 CAS、SAML、OIDC 之前，先打牢三块地基。

约 10 分钟 前置知识：无 速查：认证与 SSO 术语表

你的目标是在工作项目里集成 SSO。CAS、SAML、OIDC 三个协议看起来各不相同——有的传「票据」，有的传 XML，有的传 JSON——但它们回答的是同一个问题：

贯穿整门课程的问题 应用 B 凭什么相信「这个用户已经在别处登录过了」？

要看懂这个问题，你需要先弄清三件事：认证到底是什么；浏览器如何「记住」你已登录；为什么要把登录这件事交给一个中心。这一课就讲这三件事。

§1认证 vs 授权

想象你刚入职一家公司：

早上，你在大门口刷工牌、过人脸核验——门禁系统确认「此人是本公司员工张三」。这叫认证（Authentication，缩写 AuthN）：确认你是谁。

进门后，你的工牌能打开三楼研发区，却打不开五楼财务室——这叫授权（Authorization，缩写 AuthZ）：决定你能做什么。

顺序永远是先认证，后授权：系统得先知道你是谁，才能判断你有什么权限。

为什么要先分清这两个词 SSO 解决的是认证问题。CAS、SAML、OIDC 都是用来完成认证的协议。而常和它们一起出现的 OAuth 2.0，标准标题就叫 The OAuth 2.0 Authorization Framework——它是授权框架；OIDC 正是在 OAuth 2.0 之上补了一层「身份」，才变成认证协议。很多人分不清 OAuth 和 OIDC，根源就在这里。第 5 课细讲。

§2浏览器如何「记住」你已登录

一个关键事实：HTTP 协议是无状态的——服务器处理完一次请求就「忘了」你。打开第二个页面时，服务器并不知道你就是刚才那个人。

那网站是怎么做到「登录一次，后续页面都认得你」的？答案是 Session + Cookie 这对组合。MDN 的说法是：Cookie「使基于无状态的 HTTP 协议记录稳定的状态信息成为了可能」，首要用途就是保持用户的登录状态。

图 1 · 一次传统登录（单个应用，没有 SSO）
1
浏览器 ──▶ 应用：POST /login，携带用户名 + 密码 你在登录框输入并提交
2
应用（内部）：核对密码 ✓ → 创建 Session 记录 sid=a8f3… → 张三 这一步就是「认证」
3
应用 ──▶ 浏览器：响应头 Set-Cookie: sid=a8f3… 把会话的「号码牌」交给浏览器保管
4
浏览器 ──▶ 应用：之后每次请求自动带上 Cookie: sid=a8f3… 浏览器自动携带，你感觉不到
5
应用（内部）：用 sid 查到 Session →「是张三」→ 正常返回页面 这就是「保持登录」的真相

类比：Session 是前台的访客登记本（存在服务器），Cookie 是前台发给你的访客号码牌（存在浏览器）。你每次出示号码牌，前台翻登记本就知道你是谁。

请记住 Cookie 的一条规矩，下一节要用：浏览器只把 Cookie 发回给它所属的域名（最多放宽到同一主域名下的子域名，如 *.company.com）。完全不同的域名之间无法共享 Cookie。

你问的「有哪些认证方式」 证明身份不只靠密码——验证码、指纹、Passkey 统称认证因素；网站传递身份的技术也不只 Session + Cookie，还有 Token（JWT）、API Key、证书等。我把它们整理成了两张速查表：认证因素 与 技术机制。现在扫一眼即可，不必记。

§3SSO：把认证交给一个中心

你们公司可能有 OA、Wiki、CRM、代码仓库、报销系统……如果每个系统各自做一遍图 1 那套流程：

  • 员工要记 N 套账号密码（或干脆全用同一个弱密码）；
  • 每个系统都存一份密码，任何一个被攻破都是泄露；
  • 员工离职，管理员要去 N 个系统逐个删号；
  • 而由于 Cookie 的域名隔离，A 系统的登录状态天然无法被 B 系统看见。

SSO（Single Sign-On，单点登录）的思路是：把「认证」从各个应用里抽出来，交给一个专门的、大家都信任的认证中心——术语叫 IdP（Identity Provider）。各个业务应用不再自己核对密码。Cloudflare 总结的好处包括：用户只需一个强密码、IT 可集中执行密码策略与 MFA、凭据不再散落在各个应用里。

图 2 · SSO 的通用骨架（三大协议共有）
1
浏览器 ──▶ 应用 A：访问 OA 应用 A 发现你没有本地 Session
2
应用 A ──▶ 浏览器 ──▶ IdP：302 重定向到 IdP 登录页 同时告诉 IdP：我是哪个应用、认证完送回哪里
3
浏览器 ◀─▶ IdP：你在 IdP 输入密码——全体系唯一的一次 IdP 认证成功，并在自己的域名下种一个 Cookie，记住你
4
IdP ──▶ 浏览器 ──▶ 应用 A：重定向回应用 A，附上认证凭证 「此人已在我这里认证，他是张三」
5
应用 A（内部）：验证凭证确实来自 IdP、未被篡改 → 创建本地 Session 此后与图 1 的第 4–5 步完全相同
精妙之处：第二个应用为什么不用再输密码 现在你打开 Wiki（应用 B）。第 1–2 步照旧，被重定向到 IdP。但这一次，浏览器访问的是 IdP 的域名，于是会自动带上第 3 步时 IdP 种下的 Cookie——IdP 认出你已登录，跳过输入密码，直接签发新凭证送你回 Wiki。

回想 §2 的规矩：Cookie 不能跨域名共享。SSO 没有去打破这条规矩，而是让所有应用都把你送到同一个域名去——共享的登录状态，就存在那一个域名下。

§4三大协议地图

CAS、SAML、OIDC 都遵循图 2 的骨架。它们的区别主要在第 4、5 步：认证凭证长什么样、应用怎么验证它。

协议出身认证凭证应用如何验证常见场景
CAS 约 2001 年诞生于耶鲁大学，现由 Apereo 基金会维护 ST 票据：一次性的随机字符串 拿票据回 CAS 后台查询真伪 高校统一身份认证、政企内网
SAML 2.0 OASIS 标准，2005 年发布 断言：带数字签名的 XML 用 IdP 证书本地验签 企业员工经公司 IdP 登录各类 SaaS
OIDC OpenID 基金会，2014 年发布，建在 OAuth 2.0 之上 ID Token：带数字签名的 JWT（JSON） 用 IdP 公钥本地验签 现代 Web / 移动 / 云原生，「用 Google 账号登录」

先别背细节 这张表只是地图。现在只需记住一句话：三者骨架相同，差别在认证凭证的形态与验证方式。每个协议后面都有专门的一课。

Q4CAS、SAML、OIDC 三大协议之间，最核心的差异在于？

本课要点

  1. 认证确认「你是谁」，授权决定「你能做什么」。SSO 解决的是认证。
  2. HTTP 无状态，网站靠 Session（服务器的登记本）+ Cookie（浏览器的号码牌）记住你。Cookie 不能跨域名共享。
  3. SSO 让所有应用把用户送到同一个 IdP：重定向 → 在 IdP 登录 → 带认证凭证回来 → 应用验证 → 建本地会话。CAS / SAML / OIDC 的区别，在于凭证的形态与验证方式。
