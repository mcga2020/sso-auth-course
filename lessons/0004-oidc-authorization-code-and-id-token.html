第 4 课 · OIDC——PingFederate 的原生语言

OIDC：授权码流程与 ID Token

你们迁移的终点站。学完你会发现：它和 CAS 惊人地同构，只是票据换成了 Token。

约 14 分钟 前置：第 3 课 速查：术语表

你们的应用今天说 CAS 协议，迁移后将直连 PingFederate 说什么？OIDC。这一课走它的完整流程——放心，两次重定向、后端通道、回调地址白名单，这些概念你已经全部吃过，OIDC 只是给它们换了名字。

§1先分清：OAuth 2.0 是授权，OIDC 是认证

RFC 6749 的标题是 The OAuth 2.0 Authorization Framework——授权框架。它解决的是「让第三方应用在用户许可下访问资源」，天生不管「用户是谁」。

OpenID 基金会对 OIDC 的定义：在 OAuth 2.0 之上加一个身份层（identity layer）——具体说，就是让授权响应里多带一个 ID Token，里面写清「谁、何时、被哪个 IdP 认证、给哪个应用」。于是授权框架就升级成了认证协议。

一句话记忆 OAuth 2.0 管「能拿什么」，OIDC 管「你是谁」。你们迁移要的是后者。

§2授权码流程：完整时序（含 PingFederate 真实端点）

Web 应用的标准流程叫授权码流程（Authorization Code Flow）。PingFederate 的端点很有辨识度（官方端点文档）：

图 1 · 授权码流程：应用 oa.company.com 直连 PingFederate（共 8 步，还是两次重定向 + 一次后端通道）
1
浏览器 ──▶ 应用：GET /，无本地会话 与 CAS 流程第 1 步一模一样
2
应用 ──302──▶ 浏览器 ──▶ PF【第一次重定向：带上回调地址】 https://sso.company.com/as/authorization.oauth2?response_type=code&client_id=oa-app&redirect_uri=https%3A%2F%2Foa.company.com%2Foidc%2Fcallback&scope=openid&state=x7k2…&nonce=n9q3…
3
浏览器 ──▶ PF：PF 检查自己的会话 Cookie 没有 → 出登录页，你输密码（MFA 也在这一步）；有 → 跳过登录页直通——CAS 的 TGC 免密戏码在 PF 层重演，只是这次会话种在 PF 域名下
4
PF ──302──▶ 浏览器 ──▶ 应用【第二次重定向：前往回调地址】 https://oa.company.com/oidc/callback?code=SplxlOBeZQQY…&state=x7k2…——一次性授权码 code 抵达，state 原样带回
5
应用（内部）：核对 state —— 与第 2 步发出去的一致吗？ 不一致立即中止：这叫防 CSRF，CAS 流程里没有显式对应物
6
应用后端 ──POST──▶ PF【后端通道，不经浏览器】 POST /as/token.oauth2：grant_type=authorization_code&code=SplxlO…&redirect_uri=…&client_id=oa-app&client_secret=…
7
PF ──▶ 应用后端：JSON 应答 { "token_type": "Bearer", "access_token": "…", "id_token": "eyJhbGciOiJSUzI1NiIs…" }
8
应用（内部）：验证 ID Token（§3）→ 建本地会话 → Set-Cookie → 登录完成 从此又回到第 1 课图 1 的普通世界

第 2 步那串参数逐个拆：response_type=code 表示「我要授权码」；scope 里必须有 openid（规范原话：OIDC 请求 MUST 包含 openid scope，否则就不算 OIDC，只是普通 OAuth）；redirect_uri 就是回调地址，必须在 PF 的客户端注册里逐字符一致（老朋友又来了）。

现代标准配置：PKCE RFC 7636 定义的 PKCE：第 2 步多带一个随机密钥的哈希（code_challenge），第 6 步后端出示原值（code_verifier）——对不上就拒绝换票。它防的是授权码在传输中被截获。OAuth 2.1 草案已建议所有客户端（不限于手机 App）都启用。对接 PF 时直接按带 PKCE 写，一步到位。

§3解剖 ID Token：JWT 三段式

第 7 步拿到的 id_token 是个 JWT（JSON Web Token），长这样：

eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9  ←  Header（算法声明）
.eyJpc3MiOiJodHRwczovL3Nzby5jb21wYW55LmNvbSIsInN1YiI6IjEwMDMyIiwiYXVkIjoib2EtYXBwIiwiZXhwIjoxNzkxNjAwMDAwLCJpYXQiOjE3OTE1OTY0MDAsIm5vbmNlIjoibjlxMyJ9  ←  Payload（声明）
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ←  Signature（PF 的私钥签名）

Base64URL 是编码，不是加密——中间那段任何人都能解开看（不信把 Payload 那串丢进任意 JWT 解码器）。JWT 的安全不靠藏内容，靠签名防篡改。

Payload 里的声明（claims）对照表（均为 OIDC 核心规范 REQUIRED 项）：

声明含义验证时查什么
iss签发者（PF 的地址）必须与配置的 Issuer 精确匹配
sub用户唯一标识（你们的工号/账号）迁移关键：要能与 CAS 时代的用户名对上号
aud受众——这个 Token 发给谁必须包含自己的 client_id，别人的就拒绝
exp / iat过期时间 / 签发时间当前时间必须早于 exp（注意各机器时钟同步）
nonce第 2 步发出去的随机串必须原样带回——防重放，对不上即拒绝

验签用的公钥不用找 PF 管理员要：访问 https://sso.company.com/.well-known/openid-configuration（OIDC 发现端点），端点地址、支持的 scope、公钥集（JWKS）地址全在里面——这是 OIDC 比 SAML 舒服的地方：一个 URL 自描述一切。

ID Token vs Access Token，别混 ID Token 是给应用看的（认证结果，验完建会话就完事）；Access Token 是给 API 看的（调接口的通行证，塞在 Authorization: Bearer … 头里）。用 ID Token 去调 API、用 Access Token 判断用户身份，都是常见新手错误。

§4和 CAS 逐帧对照：你已经会一半了

骨架步骤CAS 协议（你们今天）OIDC（迁移后）
第一次重定向/cas/login?service=回调地址/as/authorization.oauth2?redirect_uri=回调地址
登录与免密输密码 → TGT/TGC输密码 → PF 会话 Cookie
第二次重定向回调 + ?ticket=ST-…回调 + ?code=…&state=…
一次性时效凭证ST（分钟级、一用即废）code（同上，且默认再叠一层 PKCE）
凭证如何变成身份回 CAS 后台查 /serviceValidate/as/token 换 ID Token，应用本地验签
本地会话建自己的 Session + Cookie完全相同

看清楚这张表：骨架六步全部同构，正是第 1 课图 2 那个通用骨架。真正的差异只有一处半——「凭证校验」从回后台查询变成了拿公钥本地验签（签名代替了查询），加上半个：参数更多、防护更细（state、nonce、PKCE）。

本课要点

  1. OAuth 2.0 管授权，OIDC = OAuth 2.0 + 身份层（ID Token）；请求 OIDC 必须 scope=openid。
  2. 授权码流程与 CAS 骨架同构：两次重定向（redirect_uri ↔ service；code ↔ ST）+ 一次后端通道（/as/token ↔ /serviceValidate）；新增 state（防 CSRF）、nonce（防重放）、PKCE（防截获）。
  3. ID Token 是签名 JWT：验证五件事——签名（JWKS 公钥）、iss、aud、exp、nonce；发现端点 /.well-known/openid-configuration 自描述一切。
  4. ID Token 给应用看，Access Token 给 API 看，各司其职。
